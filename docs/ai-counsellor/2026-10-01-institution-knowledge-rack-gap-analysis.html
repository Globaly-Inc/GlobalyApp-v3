Institution AI Knowledge Rack — gap analysis & plan

The institution-level AI knowledge, memory, voice and lead-intelligence requirements of 2026-10-01, each one read against the code on branch staging (c150c60b). Companion to 2026-10-01-globaly-ai-mvp-requirements-status (§C "AI counsellor & knowledge"), which this expands. Design precedent: 2026-09-25-institution-counselling-memory-design — most of what is asked for here is already built by it, and this document is largely about what that design deliberately left out.

Headline

The memory engine is built and it is good. Tenant-schema isolation, typed memory classes, a two-model candidate gate, contradiction detection, vote-weighted promotion, provenance and a lifecycle sweep all exist and are wired into both chat paths. Nothing in this plan should rebuild any of it.

What is missing sits on either side of it. On the input side there is no configuration object — no voice/tone profile, no data-collection rules — so an institution cannot shape its counsellor beyond 2 000 characters of free text on one widget. On the output side the learned result is invisible: there is no portal UI, so today nothing an institution's AI learns is ever seen, approved or deprecated by a human. And the whole lead-conversion half of the requirement — journeys, patterns, volunteered contact details — has no store and no detector at all.

A.3 — What the memory engine already guarantees

GuaranteeMechanism
Institution isolation institution_ai_memories lives in the institution's own tenant schema. There is no institution_id column — the schema is the boundary, so there is no owner filter anyone can forget. memory.repository.schemaFor() resolves id → schema through the pool manager; an unprovisioned institution reads empty and writes throw.
Rack isolation superadmin.match_ai_knowledge_chunks(vec, n, kind, country, institution_id) treats institution_id as exclusive: set → only that institution's sources, null → only global ones. SQL-level, not category-level.
Catalogue isolation institutions.source_job_id is unique and is the only job id handed to rag.searchAll. Empty scope answers from shared knowledge rather than another institution's courses.
Nothing personal becomes institutional Three independent filters on every candidate: the extractor's own mentions_person flag, PII_RE + the student's known names (content and free-text metadata keys), and Jev's mentions_person ≥ 0.5.
Nothing unverified becomes fact FACT_RE (money, thousands separators, test scores, years, durations) plus Jev is_fact ≥ 0.6. Confidence stored is min(extractor, jev.endorsed), and confidence alone never activates anything.
Nothing activates without a human or a crowd Learned rows enter as candidate. Promotion needs PROMOTION_MIN_ACTORS = 3 distinct hashed students, or one approve().
Contradictions do not silently win Each survivor is checked by Jev against its 5 nearest active memories; a contradicting candidate is stored with conflicts_with_id and promoteIfReady refuses it until a human clears the link.
Retired guidance stays retired Re-learning a deprecated statement returns rejected: previously_deprecated. Only a human re-statement reactivates it.
Anonymous votes cannot retire rules Widget fingerprints are client-supplied, so anonymous negatives flag (flagged_at) rather than deprecate; human-authored memories can only ever be flagged.
Provenance source, source_reference{message_id, session_id, actors[], positive_voters[], negative_voters[]}, confidence, reinforce_count, use_count, last_used_at, version, and a 30-entry history[] with the reason for each transition.
Decay Hourly sweep: expires_at passed → deprecated; a candidate unreinforced for CANDIDATE_TTL_DAYS = 90 → deprecated. Plus a recovery sweep that replays learning signals lost to a broker outage.
Read this as the floor, not the ceiling Everything in §7 of the requirement ("memory decision pipeline") and most of §14 ("privacy boundaries") is already satisfied by the above. The plan below adds to it and changes none of it.
B

Missing features — requirement by requirement

§3 · Institution-level Knowledge Rack

Needs architectural improvement

Every institution has an independent AI knowledge context: knowledge, behaviour, voice, collection rules, memory, learned knowledge, counselling patterns, lead-conversion patterns.

  • Where it exists. Six of those eight branches have a home (A.1). Two do not: data collection rules and lead conversion patterns.
  • Why it is insufficient. There is no entity called the Rack. The branches that do exist are owned at three different levels — memory per institution, knowledge per institution, behaviour per widget. An institution with two widgets (site-wide and a landing page) gets two personalities over one shared memory, and auto_learn can be on for one and off for the other while both write to the same table.
  • What should change. One row per institution holding the configuration half of the Rack. Not a new home for memories — they are already correctly placed.
  • Reuse. institution_ai_memories, ai_knowledge_sources, buildEmbedContext, the ai_widget_visitors tenant-table precedent.
  • DB / worker / API. One tenant migration · no worker · one GET/PATCH pair + portal page.
Decided 2026-10-01: business widgets stay memory-less for MVP buildEmbedContext returns rackInstitutionId: null for a business, so retrieveMemories is never called, onConversationEnd returns early on config.institution_id == null, and database/migrations/business/ has no institution_ai_memories.

The analysis offered two ways out — parity, or stating the limitation. The limitation is stated. The portal page says so instead of hiding the nav item, and both silent sites now carry a note naming this decision, so the gap reads as a choice rather than a bug to whoever finds it next.

Parity was measured, not guessed: institutionId appears 53× in memory.repository, 42× in memory.service, 25× in learning.service, 17× in the routes, plus 8 test files. Institution and business ids are both integers from different tables, so every signature would become an owner {kind, id} and the routes would move to requireBusinessOrInstitutionContext. That is a ~15-file mechanical change on a should-have, in the module where six of seven review findings came from a rule being right at one end and wrong at the other — which is the shape of change a seventh would hide in. It belongs in its own reviewed PR.

§4 · Voice & tone memory

Incorrect implementation

A configurable voice/tone profile — tone, formality, friendliness, response length, counselling style, follow-up questions, how recommendations are explained, how uncertainty is communicated, how leads are approached, proactive vs reactive. Not one large system prompt.

  • Where it exists. MEMORY_TYPES.RESPONSE_PREFERENCE, whose metadata schema is already {tone, detail_level, language, use_cards}. It is pinned by memory.repository.pinned(), so it reaches every turn regardless of similarity. Plus ai_embed_configs.custom_instructions and the hardcoded VOICE: paragraph in prompt.service.ts.
  • Why it is insufficient. renderMemoryBlock() emits "- [preference] <content>" and nothing else. The structured metadata is validated on write, parsed on read, returned to the portal — and never consulted when building a prompt. A detail_level: "brief" set by an institution changes nothing. The design doc's own note ("tone and style are RESPONSE_PREFERENCE memories") was a scoping decision that stopped one step short of applying them.
  • What should change. A typed voice profile on the Rack row, rendered as a short COUNSELLING STYLE block. Keep RESPONSE_PREFERENCE for learned style ("visitors respond better when we lead with fees") and let the explicit profile outrank it — that is exactly the config-vs-learned split the requirement asks for.
  • Reuse. prompt.service.buildSystemPrompt (one more option), sanitizeCustomInstructions, the existing pinned path.
  • DB / worker / API. Covered by the Rack row · no worker · portal form.

§5 · Data collection limitations

Missing

The Rack defines what the AI may collect: allowed, restricted, sensitive, required-for-counselling, useful-for-leads, and never-persisted.

  • Where it exists. Nowhere as policy. In practice the policy is hardcoded in two files: lib/profile-extract.ts (a fixed eight-field schema — age, gender, nationality, study_preference, qualifications, language_tests, academic_tests, work_experiences — applied identically to every institution), and services/visitor.service.ts (FIRST_ASK_AT = {3,5}, RE_ASK_GAP = {5,10}, with a comment that no institution ever asked for different numbers).
  • Why it is insufficient. Three distinct problems. (1) Compliance — gender and age are extracted from every visitor of every institution by default, with no opt-out and no stated purpose. (2) Product — a vocational college and a postgraduate business school need different fields, and a widget on a fees page should not ask for IELTS. (3) The requirement's own four-way distinction (answer-this-question / user profile / lead conversion / general knowledge) is implemented implicitly by three unrelated mechanisms and named nowhere, so nothing can be reasoned about or tested.
  • What should change. A collection block on the Rack row: which profile fields may be extracted, which are off, which are sensitive (recorded for the conversation, never persisted), and the contact-ask cadence. profile-extract builds its JSON shape from the allowed set instead of a constant; visitor.service reads the cadence instead of its constants. Both already have exactly one call site.
  • Reuse. PROFILE_KEYS / PROFILE_SCALAR_COLUMNS in lib/card-parser.ts are already the canonical field list — make them the vocabulary of the rules.
  • DB / worker / API. Rack row · no worker · portal form. No change to ai_widget_visitors: a disallowed field is simply never written.

§6 · Memory classification (A–E)

Partial — and one class is actively rejected
ClassStatusFinding
A · User-specificCorrect Rejected from institutional memory by three independent filters, and routed instead to ai_widget_visitors. Exactly the requirement. But see §13 — it is then never used.
B · General knowledgeRejected by design "What IELTS score is generally required for Australia?" is killed three times over: the extractor prompt says "If the only useful thing is a fact, output no candidate"; FACT_RE matches ielts…7; Jev's is_fact ≥ 0.6 rejects it. There is no general-knowledge store, no frequency counter, and no type for it (GENERAL_CONTEXT exists but no path ever emits it).
C · Institution-specificPartial INSTITUTION_POLICY exists but is admin-only in practice, since learned facts are blocked. The real channel is the crawled site in the Rack — which is correct, and is where institution facts belong.
D · Conversation contextMissing for widgets ai_counselor_sessions.counselling_context exists and is good — written by the update_student_context tool, which runs only in platform tool mode. Widget chats never use tools, so the column stays empty for every visitor.
E · Sensitive / restrictedPartial PII patterns and names are filtered from content and free-text metadata. What is absent is a notion of sensitive categories — health, disability, finances, immigration status, religion — which pass every current filter and would be stored verbatim in ai_widget_visitors if a model put them in a profile field.
The fix for B is small and deliberate A new type GENERAL_KNOWLEDGE with allowFacts: true, always stored as a candidate, never auto-promoted (human approval only), and tagged with the destination country/topic it concerns. That is one entry in MEMORY_TYPES, one metadata schema, and one branch in evaluateCandidate — the machinery for everything else already exists.

§7 · Memory decision pipeline

Already implemented

Extract → classify → scope → sensitivity → usefulness → confidence → deduplicate → store or discard.

  • Where it exists. learning.service.storeCandidates() runs exactly this sequence; see the flow in §E.
  • The one real gap — recurrence is exact-match only. Deduplication is sha256(normalised content) and the unique index is on that hash. "Students often ask about post-study work rights before fees" and "visitors usually raise work rights ahead of cost" are two rows, each with one actor, and neither will ever reach PROMOTION_MIN_ACTORS = 3. The requirement's "frequency / recurrence" signal is therefore unreachable for anything a model paraphrases — which is everything.
  • What should change. Before repo.insert(), reuse the embedding that was already computed for the contradiction check: if the nearest same-type active-or-candidate memory is above a merge threshold (≈0.90), reinforce it instead of inserting. One extra branch, zero extra model calls, no schema change.
  • Secondary gap. No "already known" check against the Rack chunks, so a candidate restating the crawled prospectus is stored anyway. Low priority — it costs a row, not a wrong answer.

§8 · Learning from conversation patterns

Missing

Recurring interaction sequences, stored separately from factual knowledge.

  • Where it exists. The separation is right: RESPONSE_PATTERN and STUDENT_CONCERN_PATTERN are distinct types, and TECHNIQUE_TYPES gives them their own retrieval slot (MAX_TECHNIQUES = 3) so a technique never crowds out an answer.
  • Why it is insufficient. The input is wrong. A pattern is produced by asking an LLM to read one finished transcript — "which techniques here would help future conversations?". That is a single-observation guess dressed as a pattern. Nothing anywhere labels a turn with a topic, records the order of topics, or counts transitions. "Visitors asking about Australian MBAs frequently ask about English requirements next" is unanswerable from the current data without re-reading every transcript through a model.
  • What should change. Label each turn with a coarse topic at conversation end (one cheap call, one row per session — see §D), then mine transitions with a SQL aggregate. A mined pattern is shown in the portal; a human promoting it writes a normal RESPONSE_PATTERN memory through the existing createMemory. Patterns never auto-enter the prompt.
  • DB / worker / API. One tenant table · reuses the existing learning worker at the conversation job · one portal panel.

§9 · Name & email collection

Form-only — the headline product gap

Detect naturally provided details. Do not require a form.

  • Where it exists. POST /ai-chat/guest/contact ← the contact card, and only the contact card. visitor.service.recordContact() is its single writer.
  • Why it is insufficient. lib/profile-extract.ts — the one component that reads what the visitor actually typed — has no name or email key in its output shape and never looks for one. So "I'm John, you can send it to john@example.com" leaves the visitor as status = 'visitor', with no lead, no summary email, and the contact card still queued to interrupt them three messages later. The database makes this worse: chk_ai_widget_visitors_contact_pair enforces (name IS NULL) = (email IS NULL), so even a correctly detected name-without-email cannot be stored. There is no phone column.
  • What should change. Add name, email, phone and a volunteered marker to the existing profile-extract call (it already runs on most turns and already carries the "never infer" discipline these fields need), gated by the §5 collection rules. Relax the pair constraint to "email implies name is optional". Suppress the contact card once details are held — shouldPrompt already short-circuits on contact_status = 'submitted', so the write is the whole change.
  • Reuse. extractProfile (no new model call), recordContact, recordProfile's locked read-modify-write, the generated status column (a lead classifies itself the moment the email lands).
  • DB / worker / API. One tenant migration (institution and business twins) · no worker · no new endpoint.
Decision needed — consent Writing an address the visitor typed conversationally is a different consent posture from a form they filled in. Recommended: store it, mark contact_source = 'volunteered', and have the counsellor confirm in-line ("I'll send the summary to john@example.com — is that right?") rather than silently harvesting. Confirm before building.

§10–11 · Conversion journeys & easy-conversion patterns

Missing

Not email_captured = true — the journey that led to it, aggregated across conversations.

  • Where it exists. widget-analytics.service.ts: visitors, conversations closed, conversions, conversion rate, each with a month-on-month delta and a 6-month series. That is precisely the counter the requirement rejects.
  • Why it is insufficient. None of the eleven journey questions can be answered. The raw material exists but is unjoined and split across schemas — the transcript with timestamps is globalyapp.ai_counselor_messages, the conversion is <tenant>.ai_widget_visitors.contact_submitted_at, and there is no FK between them (by design). Reconstructing a journey today means an app-level join plus a model pass over every transcript.
  • Two signals are already stored and simply unread. contact_prompt_count and contact_prompted_at_count tell you whether the AI ever asked and at which message — so "volunteered vs prompted" is derivable right now as contact_status = 'submitted' AND contact_prompt_count = 0. Likewise message_count at submission gives time-to-conversion in turns.
  • What should change. One denormalised row per finished conversation, written by the learning worker at the conversation job it already receives. Everything in §10 is a column or a short array on that row; everything in §11 is a GROUP BY over it. No event table, no stream.
  • Reuse. The conversation learning job (already fires at conversation end, already resolves the institution), learnRepo.findTranscript, the ai_widget_visitors tenant-table pattern.
  • DB / worker / API. One tenant table · existing worker, one new step · one portal panel + one analytics endpoint.
Scope discipline §11 asks for mining of historical conversations. Do not backfill at MVP: the data is there, the row can be written for new conversations from day one, and a backfill script over existing transcripts is a cheap follow-up once the shape has proved itself.

§13 · Retrieval behaviour

User-specific context is never retrieved
  • Where it exists. Institution knowledge (rag.searchAll) and institutional memory (retrieveMemories) run concurrently on both chat paths, and the ids used are persisted on the assistant message so feedback learns against exactly them. That half is complete and well made.
  • Why it is insufficient. guest.routes.ts calls buildSystemPrompt({ profile: null, … }) and passes no situation to retrieveMemories. So everything extractProfile painstakingly captured last turn — the visitor's IELTS, their degree, the course they named — is written to ai_widget_visitors and then discarded. The model sees only the last 20 raw messages. A visitor returning tomorrow is a stranger again, and situation-bound guidance cannot match because the retrieval query has no situation in it.
  • What should change. Render the visitor row through the existing rag.situationText shape and pass it as both the prompt's student-profile block and the memory query's situation. The platform path proves the pattern; the widget path just never adopted it.
  • Reuse. rag.situationText, buildSystemPrompt({ profile }), ProfileContext — the visitor jsonb columns were deliberately named to mirror platform_user_* field for field, so the adapter is a mapping, not a translation.
  • DB / worker / API. No migration · no worker · no endpoint. This is the highest value-per-line change in the document.

Carried from the MVP status doc · No portal UI

Blocking

GET|POST /institution/memories, :id/approve|deprecate|reactivate|unflag, DELETE, /institution/conversations and /:id/messages are all live and tested. No frontend file references any of them. Consequences, in order of severity:

  • Candidates are never approved, so the only promotion path is three distinct students reinforcing an identical hash — which §7 shows is nearly unreachable.
  • Conflicting candidates accumulate with conflicts_with_id set and can never be resolved, because resolution requires a human action.
  • Flagged human-authored memories (the only effect an anonymous thumbs-down has) are invisible.
  • After 90 days the sweep deprecates every unreinforced candidate — so an institution's learning silently expires without anyone having seen it.

Everything else in this plan writes into a system no one can read. The portal is phase 0.

Isolation — settled by the schema, not by this plan

Institution-level isolation is a solved problem and this plan adds nothing to it. Every object above — memories, visitors, the Rack row, the signals row — lives in the institution's own Postgres schema, resolved by schema_name through the pool manager. There is no institution_id column to omit from a WHERE, so there is no isolation code to write, no filter to review and no test to maintain. The only rule for new work is the one the existing tables already follow: a new Rack table goes in the tenant schema. Nothing else is required.

The one boundary the schema does not draw: visitor ↔ visitor Inside a single institution's schema, ai_widget_visitors holds every visitor's self-reported background, and it is read by row key — (visitor_key, embed_config_id). That row must never gain a vector column or a match function: the moment visitor data is retrievable by similarity, one visitor's answer can surface another's facts, and the schema boundary says nothing about it. This is a constraint on §D's new tables, not a task.

Data model

Two new tables and a handful of columns. Everything else is reuse.

★ New — institution_ai_profile (tenant schema, one row)

As built

The Rack's collection block now carries one standing line — confirm an address back once before relying on it — rendered whenever email is collectable, which is the default. The model sees the address in the message it is answering, so the confirmation lands in that same reply.
  • A name alone is now storable. chk_ai_widget_visitors_contact_pair is dropped: it described the CARD, where both fields are asked for, and it refused the real case of a visitor who says only “I'm John”. Phase 5 — Pattern mining Built 2026-10-02

Topic labelling at conversation end, transition counting over institution_conversation_signals.topic_sequence, a portal panel showing mined sequences with support counts and a promote-to-memory button. Deliberately after MVP: it needs a corpus, and a pattern mined from twenty conversations is noise.

As built — no new endpoint, no new table, no new slice

Same tenant, same read, same 4th tab, same Redux slice — a separate route would have added a thunk, a slice and a second round trip to show four rows beside figures the page already fetched.
  • Support counts CONVERSATIONS, not occurrences. count(DISTINCT s.id) over adjacent pairs from jsonb_array_elements_text(...) WITH ORDINALITY, joined b.i = a.i + 1. A journey that oscillates fees→visa→fees→visa contributes one; counting rows would have made one restless visitor look like three. Verified against the real planner, and against a synthetic VALUES corpus where the two numbers differ (3 vs 4).
  • A floor, because the deferral reason is still true. MIN_TRANSITION_SUPPORT = 3 in SQL (HAVING), and the panel prints the corpus size beside the list so the reader can discount the rest. Two visitors doing the same thing is a coincidence, and inviting someone to teach it to their counsellor is worse than showing nothing.
  • The sentence is composed on the BACKEND (transitionGuidance in lib/conversation-topics.ts, beside the vocabulary it names) and returned as suggestion. Tenant isolationNot a risk The tenant schema is the isolation. There is no filter to forget and nothing to verify. Keep new Rack tables in the tenant schema and it stays true by construction.
PrivacyMedium Three open items. (1) COUNSELLOR_CORRECTION is stored verbatim with allowFacts: true and only a person check — a counsellor who pastes a student's details into a correction creates an active memory containing them. Add the PII regex to the correction path. (2) ai_widget_visitors has no TTL and no erase endpoint; a GDPR/DSAR request today has no handler. (3) Phase 2b widens what the AI reads out of prose — ship it default-on for email only.
Memory contaminationLow Four independent gates already. The residual path is metadata free-text keys, which are filtered by an explicit list — FREE_TEXT_METADATA_KEYS. Adding a free-text metadata field without adding its key silently reopens the hole. The schema file says so; the test enforces it.
Incorrect learningMedium Candidates need 3 distinct actors or a human. With no portal (today) the human path does not exist and the crowd path is unreachable for paraphrases — so in practice nothing is being learned and candidates expire at 90 days. Phases 0 and 4 are the fix; until then, learning is inert rather than wrong, which is the safe failure.
Hallucinated memoriesLow Two models must agree (confidence is the minimum of extractor and Jev), facts are refused, and nothing enters the prompt as a fact — learned rows render "(learned, advisory)". Residual: with TYPESAFE_API_KEY unset, Jev returns null everywhere and the pipeline falls back to regex plus the extractor's own self-assessment. Confirm the key is set in staging and production, or the second opinion is silently absent.
Prompt sizeMedium Memory is budgeted (800 + 1 700 chars). Nothing else is. Adding the Rack profile (~250) and visitor context (~400) is fine; the uncapped risk is ragContext. Give the new blocks explicit budgets like the memory renderer has, and log the assembled prompt length so growth is visible before it is expensive.
CostMedium Each widget turn already costs: 1 chat + 1 embedding + extractProfile + conditionally judgeConclusion. Phase 2 adds none. Phase 3 adds one lite call per conversation. Phase 5's labelling must ride that same call, not add another. Per extraction cost priority, add per-institution AI usage accounting before enabling anything in Phase 4/5 broadly.
PerformanceLow Memory retrieval is an exact cosine sort over hundreds of rows in one schema, guarded by a 60 s zero-count cache that skips the embedding entirely when an institution has nothing. The HNSW upgrade path is documented in the migration. Watch pool count instead: every institution with an active widget holds a tenant pool.
Duplicate memoriesMedium Exact-hash dedupe only. This is the single biggest brake on learning quality and it is Phase 4's first item.
Lead attributionMedium Conversion is contact_status = 'submitted' on a row keyed by sha256(fingerprint + embed_key). A cleared browser, a second device or a private window is a new visitor and a new "conversion"; the same person may convert twice. State this on the analytics panel rather than implying precision. contact_source at least separates volunteered from prompted, which is the distinction the requirement actually asks about.
Business widgetsMedium No memory, no learning, no error — a silent capability gap that will be read as a bug the first time someone demonstrates it. Either ship parity in Phase 4 or say so in the portal.
J

Implementation recommendation

Build the portal first, and build nothing else until it exists. The memory engine is already better than the requirement asks for, and it is currently inert: every candidate it produces expires unseen after ninety days because the only two promotion paths are a human who has no screen and a crowd threshold that paraphrasing makes unreachable. Adding voice profiles, collection rules and journey tables on top of an unobservable engine multiplies the amount of invisible state. Phase 0 is a frontend-only change against endpoints that already ship.

Then take the two retrieval fixes in Phase 2, in that order. Feeding the visitor's own context back into their prompt is roughly fifty lines against APIs that exist on the platform path, and it fixes the most visible product failure in the system — a counsellor that forgets what it was told one message ago. Volunteered contact detection is the second, and it turns a form into a conversation.

Add exactly one new configuration object, not a system. The Rack should be one tenant row with four typed JSONB blocks. Resist a settings table per concern, a versioned config chain, and a behaviour-rules engine — the 2026-09-25 design already made the same call about settings and events tables and was right to. Voice and collection rules are read whole, written whole, and will change a few times a year.

Keep patterns and journeys as queries, not pipelines. One denormalised row per finished conversation answers every question in §10 and §11 with a GROUP BY. An events table, a stream, or a scheduled aggregation job buys nothing at this volume and costs a worker, a queue and a backfill each.

Reuse list, explicitly. institution_ai_memories (all memory — add types, never tables) · match_institution_ai_memories · createMemory / approve / voteOnMemory / runSweep · the institution_memory_learn queue and its worker · lib/jev.ts · evaluateCandidate · retrieveMemories and renderMemoryBlock · rag.situationText and buildSystemPrompt · extractProfile · ai_widget_visitors and its generated status column · sanitizeCustomInstructions · the pool-manager tenant resolution in memory.repository.schemaFor. Nothing in this plan needs a second memory system, a second vector store, or a second queue.

Four decisions needed before Phase 1 starts
  • Consent posture for volunteered contact details — store silently, or confirm in-line? (Recommended: confirm.)
  • Default collection rules — should gender and age stay on by default? (Recommended: off; they are collected today with no stated purpose.)
  • Business widgets — memory parity in Phase 4, or documented as institution-only for MVP?
  • General knowledge — is an institution's counsellor allowed to learn generic sector facts at all, or should everything factual come from the Rack and the catalogue? (Recommended: allow, human-approval-only, default off.)
