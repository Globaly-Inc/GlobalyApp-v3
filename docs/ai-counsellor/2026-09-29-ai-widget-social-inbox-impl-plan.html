AI Widget Social Inbox

Let a business or institution connect its Facebook Page, Instagram account and WhatsApp number to its AI widget. Direct messages land in one inbox next to website chats. The same AI answers them, and a team member can read every thread and reply by hand.

Date
2026-09-29
Mode
New feature, extending the AI embed widget (ai_embed_configs)
Spec
None yet. No PRD or spec covers social channels (searched docs/). This plan records the design decisions; §10 needs answers before any code.
Reference
GlobalyOS-V2 Support inbox (inbox-webhooks-meta.ts, normalize.ts, inbox-send.ts). Its patterns are reused and its known gaps are fixed here.

01Summary

Website widget (exists) Messenger Instagram DMs WhatsApp

In scope

  • Connect channels from the AI widget page. Facebook Login for Business covers a Page plus its linked Instagram account. WhatsApp uses Embedded Signup. Each connection belongs to one widget and uses that widget's knowledge scope, instructions and monthly credits.
  • Receive DMs through one signed Meta webhook. Each sender becomes a thread in the existing widget tables: ai_counselor_sessions and ai_counselor_messages centrally, and ai_widget_visitors per tenant.
  • AI auto-reply per channel (toggle), using the same answer pipeline as the website widget, turned into plain text that fits each channel's length limit.
  • Inbox at /business/ai-widget/inbox: every widget conversation (website and social) with channel filters, the full transcript and a reply box for social threads.
  • Human takeover: a staff reply pauses the AI on that thread, and so does a reply sent from Meta Business Suite (detected from message echoes). "Resume AI" turns it back on.

Out of scope

  • Post and ad comments, TikTok, Telegram, SMS, email.
  • Broadcasts and marketing messages. WhatsApp template sends for threads past 24 hours are Phase 3.
  • Sending images or files. Inbound media is recorded as a placeholder until Phase 3.
  • Pushing staff replies into an open website widget. Website threads are read-only in the inbox.
  • Assignment, SLAs, AI confidence gate and intent lists. These were deliberately skipped when porting from GlobalyOS.
  • The HUMAN_AGENT message tag (7-day window). It needs separate Meta approval.

02How messages move

Four paths. Each writes to the tables the website widget already uses, so the inbox, the visitor record and the AI history read one conversation, not a copy.

Inbound DM

  1. Meta calls POST /api/v3/social/webhooks/metaOne URL for the whole app. Meta registers a single callback per app, not per Page.
  2. Verify X-Hub-Signature-256 against the raw bodyHMAC-SHA256 with the app secret, timingSafeEqual. Reject with 401 before any JSON parse or DB read.
  3. Parse events by objectpage and instagram use entry[].messaging[]. whatsapp_business_account uses entry[].changes[].value.
  4. Find the channel row by (channel, account id)This gives the widget, and the widget gives the tenant. The account id is covered by Meta's signature.
  5. Find or create the session and tenant visitor, then insert the messageThe unique index on external_message_id makes Meta's retries harmless.
  6. Publish { sessionId, messageId } to social_inbound, answer 200If the DB write fails, answer 5xx so Meta retries.

AI reply (worker)

  1. Wait about 4 s, then check shouldAutoReply()Skips if AI is off or paused, a newer message is waiting, there's no text, the sender cap is hit, or the widget is inactive.
  2. Run answerVisitorTurn()This is the website widget's pipeline moved into a service, called with channel and a no-op onChunk.
  3. Convert with toChannelText()Removes widget blocks and cards, converts markdown, splits to the channel's limit.
  4. Send through the Graph API with the sealed channel token
  5. Insert the assistant row with Meta's message idIf the send fails, the row is kept with delivery_error so the inbox shows "Not delivered".

Staff reply

  1. Inbox composer calls POST /api/v3/ai-chat/embed/visitors/:id/messages
  2. Load the visitor through req.dbThe tenant schema is the ownership check.
  3. Check replyWindowOpen()24 h since the customer's last message. Returns 409 with a plain explanation if closed.
  4. Send through Graph, insert role='assistant' with sent_by_platform_user_id
  5. Set ai_paused_at on the visitorThis stops the AI and the person answering at the same time.

Reply from Meta Business Suite

  1. Meta sends an echo (message.is_echo) for every Page message
  2. Echo with our app_idIgnore it, because we already stored it at send time.
  3. Echo from any other app, or noneStore it as a staff reply with no user id and pause the AI. The transcript stays complete and the AI stops answering.

Channel limits the code has to respect

ChannelAccount idSender idSend endpointText limitReply window
MessengerPage idPSID (page-scoped)POST /{page-id}/messages2,000 chars24 h after the user's last message (messaging_type: RESPONSE)
InstagramIG professional account idIGSIDPOST /{page-id}/messages1,000 bytes UTF-824 h after the user's last message
WhatsAppphone_number_idwa_id (phone)POST /{phone-number-id}/messages4,096 chars24 h service window, then approved templates only

Graph errors to handle by name: 190 is an invalid token, so mark the channel "Needs reconnect". 10 with subcode 2018278 is a Messenger or Instagram send outside the window. 131047 is a WhatsApp send past 24 hours. The Graph version is pinned in META_GRAPH_VERSION; set it to the current version at build time.

04Database track

Three decisions keep this small:

  • No new conversation or message tables. A social sender is a visitor thread like any website visitor.
  • No change to the role CHECK. A staff reply is role='assistant' with sent_by_platform_user_id set. The model history already reads the org's side of the conversation as assistant, so no history reader changes.
  • Visitor key. Social threads use visitor_key = sha256("<channel>:<account id>:<sender id>"). The embed key is left out on purpose: rotating a widget's key must not split a customer's Messenger thread. Isolation between widgets still comes from the (visitor_key, embed_config_id) unique index.

globalyapp · ai_social_channels (central, like ai_embed_configs)

This is central, not per tenant, because the unauthenticated webhook has to find the owner from the Page id before it can know which schema to use.

-- 20260929_002_ai_social_channels.ts (knex; SQL shown for review)
CREATE TABLE ai_social_channels (
  id                    serial PRIMARY KEY,
  embed_config_id       integer NOT NULL REFERENCES ai_embed_configs(id),
  channel               text NOT NULL
                        CONSTRAINT ai_social_channels_channel_check
                        CHECK (channel IN ('messenger','instagram','whatsapp')),
  external_account_id   text NOT NULL,      -- page id | IG account id | phone_number_id
  external_parent_id    text NULL,          -- linked page id (IG) | WABA id (WhatsApp)
  display_name          text NOT NULL,      -- page name, @handle, +61 4xx…
  access_token_sealed   text NOT NULL,      -- seal() from shared/crypto/secret-box.ts; never selected into a reply
  ai_auto_reply         boolean NOT NULL DEFAULT false,
  status                text NOT NULL DEFAULT 'active'
                        CONSTRAINT ai_social_channels_status_check CHECK (status IN ('active','error')),
  last_error            text NULL,
  last_webhook_at       timestamptz NULL,
  connected_by_platform_user_id integer NULL REFERENCES platform_users(id),
  created_at            timestamptz NOT NULL DEFAULT now(),
  updated_at            timestamptz NOT NULL DEFAULT now(),
  deleted_at            timestamptz NULL
);
-- One Page / number can feed one widget. Named: the connect route maps 23505 on it to
-- "This Page is already connected to another widget."
CREATE UNIQUE INDEX ai_social_channels_account_uniq
  ON ai_social_channels (channel, external_account_id) WHERE deleted_at IS NULL;
CREATE INDEX ai_social_channels_config_idx
  ON ai_social_channels (embed_config_id) WHERE deleted_at IS NULL;

05Authorization track

This repo has no RLS. Row access comes from the tenant schema (req.db) and explicit owner filters. Each new surface states its check.

SurfaceWho can reach itCheck
Channel routesBusiness or institution staffrequireBusinessOrInstitutionContext. The channel's embed_config_id must belong to recipientFromRequest(req), otherwise 404 (not 403, so ids don't leak).
Visitor transcript and replySameVisitor is loaded through req.db. A visitor from another tenant does not exist in that schema.
Webhook POSTMeta onlySignature over the raw body with the app secret. The tenant comes only from the channel row found by the signed account id.
Webhook GETMeta setuphub.verify_token compared in constant time with meta_webhook_verify_token.
OAuth callbackBrowser redirect from Facebookstate is seal()ed and holds org kind, org id, widget id, user id and expiry (10 min), and is single-use in Dragonfly. The JWT isn't sent on this redirect, so the state is the identity.
Data-deletion callbackMetaVerify the signed_request with the app secret, then delete that sender's visitor rows and messages.
TokensServer onlySealed at rest. Every response is an explicit column allow-list, and access_token_sealed and external_user_id are never on one.

Steps

  • Move the answer pipeline out of the route first. Move /guest/messages steps 1–13 (resolve config and credits, context, session, visitor, history, RAG, prompt, streamChat, parse, profile extract, usage, persist) into answerVisitorTurn({ config, visitorKey, content, channel, onChunk }). The route keeps its SSE writer and the contact and end-of-chat cards. Existing embed tests must pass unchanged before anything else is added.
  • Webhook route. Register it in its own encapsulated plugin with addContentTypeParser("application/json", { parseAs: "buffer" }) so only this route sees raw bytes. Override the global IP rate limit on the route, because Meta sends bursts from shared IPs and the signature check comes before any work.
    • Respond 200 for ignored events: statuses in P1, our own echoes, unknown accounts. Log the unknown ones.
    • Respond 5xx only when persisting fails, so Meta retries into the dedup index.
    • Update last_webhook_at on the channel for its health pill.
  • recordInbound: findByVisitor/createForVisitor with the social visitor key; tenantDbFor(config); resolveVisitor with channel fields; fetch the sender's name once on first contact (GET /{psid}?fields=first_name,last_name; IG fields=name,username). Don't store profile photo URLs; Meta's CDN links expire.
    • Insert the user message with external_message_id. Publish only if a row was actually inserted.
    • Non-text messages are stored as [Photo], [Voice message] and so on, with the type in attachments. The AI skips them.
    • Clear owner_read_at so the thread shows as unread.
  • shouldAutoReply() returns a reason, not a boolean. The reasons, in order:
    1. channel_ai_off
    2. paused_by_staff
    3. config_inactive
    4. no_text
    5. newer_message_pending (so three quick messages get one answer)
    6. sender_cap (30 AI replies per thread per hour, so a stranger can't drain a widget's credits by DM)
    The credit_limit 429 from resolveActiveConfig is caught as a reason too. Log every skip at info with its reason.
  • Worker social-reply.worker.ts: queueService.consume(SOCIAL_QUEUES.INBOUND), a 4 s in-handler wait before the gate, then answer, toChannelText, sendReply. Four wiring edits: worker file, job:social-reply, compose service, Makefile targets.
    // ponytail: 4 s in-handler wait holds one consumer slot per message; move to a delayed queue if volume grows
  • meta-graph.ts: plain fetch with a 15 s AbortSignal.timeout (the same lesson as the extraction LLM freeze: an unbounded external call froze a worker). It maps 190 → set channel status='error' with last_error, and the window codes → a typed error the staff route turns into 409.
  • Prompt: when channel is set, the system prompt says to answer in plain text, two short paragraphs at most, with no card, chip or block syntax. Course cards the model still produces become at most three "Name: link" lines in toChannelText.
  • Settings: Meta app id, secret, webhook verify token and the Login config ids go through getIntegrationSetting() (encrypted, 60 s cache, env fallback). No secrets in .env without your go-ahead.
  • P2 WhatsApp: Embedded Signup returns code, waba_id, phone_number_id. Exchange the code for a business token, POST /{waba-id}/subscribed_apps, POST /{phone-number-id}/register if the number is new. Webhook branch whatsapp_business_account, contacts[].profile.name → visitor name, wa_id → phone. Send { messaging_product: "whatsapp", to, type: "text", text: { body } }. WhatsApp keeps *bold* and _italic_; the others get plain text.

08Test plan

Standalone backend/tests/*.ts scripts run with npm run test:<name>. For each guard, break it on purpose and watch the test go red for the right reason before it counts. Undo the break with the same targeted edit, never git checkout.

  • Tracer bullet: tests/social-meta-events.ts. Real-shaped Messenger, Instagram and WhatsApp fixtures → parseMetaEvents. Asserts channel, account id, sender, mid and text. Asserts that echoes carry app_id, that statuses[] and read events produce nothing, and that an unknown object produces nothing.
  • tests/social-meta-signature.ts: valid passes. A tampered body, the wrong secret, a missing header, a header without sha256=, and a signature of the wrong length each fail with their own reason and never throw (timingSafeEqual throws on length mismatch if not guarded).
  • tests/social-outbound-text.ts: splits at 2,000 characters, 1,000 bytes (an emoji-heavy fixture proves bytes, not characters) and 4,096 characters, on paragraph then sentence boundaries. No chunk goes over its limit. Widget blocks are removed. Markdown becomes plain text except WhatsApp bold and italic.
  • tests/social-reply-gate.ts: one case per reason, in order, plus the window boundary at exactly 24 h.
  • tests/social-inbound-dedup.ts (dev DB, like rerun-agentcis.ts): the same mid delivered twice gives one row, one publish, and the conflict is on ai_messages_external_id_uniq. Deletes its own rows at the end.
  • tests/social-visitor-key.ts: the key changes with channel, account and sender, never equals the website key for the same inputs, and is stable across embed-key rotation.
  • Regression after the pipeline move: embed-visitor-key, embed-rate-limit, embed-owner-profile, ai-tool-loop and ai-counsellor-flow stay green with no edits to the tests.
  • End to end in Meta Development mode: a test Page where the dev is an admin, a tunnel for the webhook URL, DM from a tester account → AI answers → staff replies from the inbox → AI pauses → reply from Business Suite → echo recorded.
  • Gates: npm run build (backend tsc), npm run lint (frontend), a secret grep over the diff, and every new response checked against its allow-list.
