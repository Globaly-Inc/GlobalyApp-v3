Complete-crawl failure analysis

Every point at which the extraction pipeline can lose a page or an entity without reporting it. Read from the source on 2026-10-01, branch dev-feat-ai-widget-counseling. Line references are accurate as of that commit and will drift.

The one-sentence answer

No — the current architecture cannot guarantee complete site scraping, and the gap is structural rather than a matter of tuning. Discovery is a single-shot, first-source-wins lookup with no graph traversal, so a page that no sitemap lists and the homepage does not link is unreachable by construction; and completion is defined as no page is pending or processing, which counts a permanently failed page as a finished one. Those two facts together mean a job can report review with 100% progress while an arbitrary fraction of the site was never discovered, never fetched, or fetched and discarded.

A. Current completeness model

The pipeline has no explicit definition of complete. Completeness is an emergent property of three independent checks, none of which was written to answer the question "did we get the whole site?".

1. Discovery is "complete" when one source answered

discoverUrlsForCrawl (lib/scraper.ts:1176) is a first-success-wins cascade, not a union:

1. Firecrawl map        → if (map.success && map.links.length > 1) RETURN
2. sitemap ∪ catalogue ∪ cert-log → if (merged.length > 1)     RETURN
3. seed page links      → if (res.links.length > 1)            RETURN
4. [seedUrl]                                                   RETURN

The branches are mutually exclusive. A Firecrawl map that returns two URLs short-circuits every sitemap source permanently — robots.txt declarations, sitemap indexes, catalogue subdomains and the Certificate-Transparency probe are all skipped. The per-source accounting (sources, added after the Yale incident) reports the zero-yield of a source within a branch, but cannot report a branch that never ran.

2. Page processing is "complete" when nothing is pending or processing

checkAllPagesDone (lib/queue-completion.ts:44):

count(*) filter (where status in ('pending', 'processing')) as remaining
...
if (Number(counts?.remaining) === 0) { /* advance to verification */ }
This is the single most consequential line in the pipeline. failed is not in that filter. A page that exhausted its retries, or that the reclaim sweep gave up on after three stale reclaims, is terminal — and terminal is treated as done. The job advances to verification and then to review with its failures recorded only as pages_failed and a scatter of page_error timeline rows that nothing gates on.

3. The job is "complete" when the queue is empty or discovery found nothing new

runQueuePages (lib/pipeline-steps.ts:509) writes status: "review" when idle — nothing newly queued and nothing live. The docstring is explicit that the denominator of the progress bar is what was queued, not what was found, because URLs refused at page_cap "were thrown away and can never be scraped, so counting them holds a finished job below 100%". That is a deliberate decision to make a truncated crawl display as 100% complete.

What the model does guarantee

Credit where due — the hard parts of exactly-once logical processing are solved properly, and better than most pipelines of this size:

  • DB unique constraint on (job_id, url) is the real dedupe, not a check-then-insert.
  • attempt_token fencing makes a slow-but-alive worker's writes a no-op after reclaim.
  • Atomic claim (status IN ('pending','failed') → 'processing') kills duplicate messages.
  • The LLM result cache keys on the full prompt hash, so an unchanged page costs nothing on re-run.
  • LLM_TOTAL_BUDGET_MS (12 min) is deliberately under STALE_MINUTES (20) so a slow model call cannot trigger a false reclaim.

The gap is not in the machinery. It is that the machinery is asked the wrong question.

B7. Secondary pages — asked about specifically

The caches do exactly what they were built for. The cap does something else.

MechanismScopeBehaviourVerdict
curriculumCacheper messageURL → parsed units; a second variant reuses it and clears currUrlCorrect
secondaryPageCacheper messageMemoises failures too (null), so one dead link costs one attempt, not fortyCorrect
markupCacheper messageCourseLeaf table parse result; settles units with zero LLM spendCorrect
fetchable()per messagesecondaryPageCache.has(u) || secondaryFetches < CAP — a cached URL is still served past the capCorrect
SECONDARY_FETCH_CAP = 20per message The 21st distinct curriculum/fees page on one listing is silently skipped — no event, no queue row, no flag on the course Silent loss
The shared-page case is solved; the distinct-page case is not. Your example — A, B, C all pointing at curriculum page X — costs exactly one fetch and is correct. The failure is the opposite shape: a listing page with 40 courses each having its own curriculum page. Twenty are fetched. Twenty are dropped. Those courses are written to staging with no study units and nothing marks them as incomplete, so they are indistinguishable from courses that genuinely publish no curriculum.

Better strategy: stop treating secondary pages as an inline side-effect. A secondary page is a page. Queue it as a first-class row with page_role = 'secondary' and a parent_course_id, let the normal worker, retry, reclaim and completion machinery own it, and let the per-job budget — not a per-message counter — decide what gets deferred. The cap then becomes a scheduling priority rather than a silent discard, and a deferred secondary page is visible as deferred.

C. Silent data-loss risks, ranked

These are the cases where the system reports success and the data is simply not there. Ranked by expected volume lost × likelihood of going unnoticed.

  1. Permanently failed pages do not block completion. queue-completion.ts:48. A scraper outage can fail hundreds of pages; the job still reaches review and the business-facing status reads progress_pct: 100.
  2. Discovery short-circuit. scraper.ts:1181. A thin Firecrawl map suppresses every sitemap source. The per-source warning cannot fire for a source that never ran.
  3. Snapshot cap of page_cap. pipeline-steps.ts:216. 9,500 of 10,000 discovered URLs are never fetched, and the URL classifier then judges them without an excerpt — making it more likely they are also mis-categorised as other.
  4. page_cap discards classified course URLs. Reported in the timeline as a warning, then erased from the progress denominator by design.
  5. Markdown truncated at 120k chars. No event. The largest catalogue pages — exactly the ones with the most courses — lose the most.
  6. Gemini output truncated at 65,536 tokens. Detected, correctly not cached, and then used anyway. The courses past the cut never existed as far as staging is concerned.
  7. Secondary-fetch cap of 20. Courses silently staged without curriculum.
  8. filterUrls hyphen over-match. /media-studies, /privacy-law-llm and friends never enter the site list at all — the earliest and hardest drop in the pipeline.
  9. Step worker death wedges the job. Not loss, but indefinite stall with no alert — and an operator who eventually force-resumes may not realise the snapshot was partial.
  10. Partial HTML accepted as a complete page. Stored as the snapshot, hashed, and then treated as unchanged on every subsequent run — so the error becomes sticky.

D. Hard guarantees vs assumptions

Guaranteed by code

  • A queue row is processed by at most one attempt at a time — atomic claim + attempt_token.
  • A duplicate queue message is a no-op.
  • One (job_id, url) yields at most one queue row — DB unique constraint.
  • A crashed page worker's row is reclaimed within STALE_MINUTES + 5 min, up to 3 times.
  • An unchanged page + unchanged prompt costs no model tokens — extraction_llm_cache on the full input hash.
  • A truncated or JSON-repaired model answer is never cached.
  • Every external fetch is bounded (EXTERNAL_FETCH_TIMEOUT_MS, SITEMAP_FETCH_TIMEOUT_MS, LLM_REQUEST_TIMEOUT_MS, LLM_TOTAL_BUDGET_MS).
  • Per-host pacing is serialised across processes via extraction_host_slots.
  • Verification cannot start while a discovery step is failed or in flight.

Probabilistic — works most of the time, no guarantee

  • Course-URL identification: heuristic, then an LLM narrowing pass protected only by a 25% floor (classifierDistrusted).
  • Course extraction itself: no floor, no cross-check, no count reconciliation.
  • Catalogue-subdomain discovery: a 9-word list, plus crt.sh ranked and capped at 25.
  • Soft-404 detection: four regexes over page text.
  • Anti-bot escalation: two tiers, then give up.

Assumptions baked in, never checked

  • That a sitemap or Firecrawl map is the site. Nothing ever measures coverage against the live link graph.
  • That page_cap is a budget rather than a correctness boundary — it is currently both.
  • That 120,000 chars contains the whole page.
  • That a page returning ≥200 chars without a 404 phrase is complete.
  • That a failed page is acceptable collateral.

Undocumented behaviour worth writing down

  • nack(requeue=false) with no DLX — messages are destroyed on an uncaught throw.
  • dispatchSnapshotBatches silently applies page_cap to the snapshot set; the parameter is named pageCap but its effect on discovery coverage is not noted anywhere.
  • Snapshot order is unspecified DB order, so which 500 of 10,000 URLs get fetched is effectively arbitrary.
  • Secondary pages are outside the queue state model entirely.
  • onlyMainContent is a snapshot-store key; whether main-content stripping actually occurs depends on the scraper tier. Worth re-verifying for the Crawl4AI and Firecrawl paths — the Scrapling path was fixed to always pass main_content_only=false.

E. Proposed complete-crawl architecture

Keep everything that works — the queue machinery, fencing, reclaim, the result cache, the snapshot store, the step chain's inspectability. The change is to put a frontier in front of it and a ledger behind it.

The six principles

    
    
      
  1. Union, never first-win. Every discovery source runs, always. They are
        cheap relative to one Gemini call and they disagree constantly.
    2. 
      
  2. The frontier is the crawl. Discovery is not a step that finishes; it is a
        state that drains. A page's links go back into the frontier. The job cannot complete while
        the frontier is non-empty.
    3. 
      
  3. Caps defer, they never discard. page_cap becomes a
        rate budget: past the cap, URLs are parked in state deferred, counted,
        and resumable. A truncated crawl must be visible as truncated.
    4. 
      
  4. Deterministic before probabilistic. Structured data and known table
        shapes are free and exact. The model sees only what survives that pass.
    5. 
      
  5. Fetching and understanding are separate budgets. HTTP is cheap and should
        be exhaustive; Gemini is expensive and should be selective. Today they are coupled through
        page_cap, which is why completeness and cost are in direct conflict.
    6. 
      
  6. Completion is proved, not inferred. See F.

The completion predicate


job_complete(J) ⟺
    (1) no url in J is in state frontier | fetching | retry_wait | deferred
AND (2) no discovery or extraction worker holds a claim on J
    (proved by: no in-flight claim token, and no step in 'processing')
AND (3) every url is in exactly one of:
        extracted | irrelevant | partial | failed_permanent
AND (4) ∀ url in partial ∪ failed_permanent:
        the url carries a machine-readable reason
AND (5) count(partial) + count(failed_permanent) is either 0
        (→ complete_clean)
        or has been explicitly acknowledged by an operator
        (→ complete_with_gaps)

      extracted yet, and you can extract the rest later without re-crawling.

Critical — silent loss, fix before scaling

  1. Union every discovery source. lib/scraper.ts:1176 discoverUrlsForCrawl — run map, sitemap, catalogue, cert-log unconditionally and merge. Keep method for the timeline, add every source's count to sources. Removes the largest single completeness hole for a few extra HTTP calls.
  2. Make failed block completion. lib/queue-completion.ts:48 — add a permanent-failure count to the gate; introduce complete_with_gaps rather than letting review mean both things.
  3. Stop discarding at page_cap. lib/staging-writer.ts:2812 insertQueueItemDetailed — insert with status: 'deferred' instead of refusing. lib/pipeline-steps.ts:216 dispatchSnapshotBatches — stop slicing the URL list; batch all of it.
  4. Fix the filterUrls hyphen over-match. lib/html-utils.ts:395 — replace \b with a full-segment anchor. One-line change; recovers whole families of legitimate programme pages.
  5. Surface truncation. lib/html-utils.ts:475 truncateMarkdown — return whether it cut, write a page_truncated event, and set the page row to partial.   6. Declare a dead-letter exchange on every queue in shared/queue/queueService.ts, and alert on DLQ depth.
  7. Add a step-staleness sweep alongside extraction-queue-reclaim.worker.ts — a step stuck in pipeline_progress = "processing" past a threshold is republished or marked failed. Today it wedges the job permanently via the inFlightStep guard.

Critical — cost, measured in G2

  1. Fix the course_extraction cache key. lib/llm-client.ts inputHash hashes the whole prompt, which now includes recallMemory()'s nearest-neighbour examples. Those shift as extraction_memory grows, giving a 0.0% hit rate across 839 calls. Key on (page content_hash, prompt_version, model, lookup_version) and keep the volatile addendum out of the key.   2. Add a deterministic zero-yield gate before the full-model call. 85% of Curtin's extraction calls returned no course.   3. Set LLM_MODEL_PRICES. It is unset, so totalCostUsd returns null and no job can report what it cost. Every cost decision is currently being made without the number.

Important — completeness ceilings

  1. Introduce the frontier. New table extraction_url_frontier (url, canonical_url, depth, state, discovered_via, etag, last_modified, content_hash) and a crawl step that loops until drained. Harvest links in the page worker — the data is already in page.links and currently only a pagination regex reads it.
  2. Promote secondary pages to queue rows (page_role, parent_course_id). Retires SECONDARY_FETCH_CAP as a silent discard and puts curriculum fetches under the same retry and reclaim guarantees as everything else.
  3. Split the queue states per section F. Migration is additive: failed_permanent, partial, deferred, irrelevant, plus a reason column.
  4. Widen the completion guard beyond DISCOVERY_STEP_ORDER to every step that can produce queue rows (courses, discovery).

  6. Chunk long pages rather than truncating at 120k.
  7. Batch runQueuePages — one insert statement and one publish batch per chunk, and split the step across messages like site_snapshot does.

Final answer

Can the current architecture guarantee complete site scraping? No.

It is a well-engineered best-effort pipeline. The exactly-once machinery, the fencing, the reclaim sweep, the bounded timeouts and the result cache are genuinely solid — better than the median system of this size, and most of the comments in the source record a real incident that produced them. None of that is the problem.

The problem is that completeness was never made a property the system can hold. Three specific facts put a ceiling on it:

  1. Discovery cannot reach the whole site. It is a single-shot, first-source-wins lookup with no graph traversal. A page in no sitemap and not linked from the seed is unreachable by construction, not by misconfiguration.
  2. Caps discard rather than defer. page_cap and the snapshot slice throw URLs away, and the progress denominator is then taken from the queue, so a truncated crawl displays as 100%.
  3. Completion counts failures as finished. pending|processing is the only thing that holds a job open, so permanent failures, truncated pages and skipped secondary fetches all pass through the gate invisibly.

Moving to an eventually-complete crawl with explicit failure accounting requires exactly three structural changes:

  1. A frontier — discovery becomes a state that drains rather than a step that finishes, fed by unioned sources and by links harvested from every page fetched.
  2. A state model with partial, deferred and failed_permanent — so that "we did not get this" is representable at all, which today it is not.
  3. A completion predicate that is proved rather than inferred — the frontier is empty, no worker holds a claim, every URL is terminal, and every gap is acknowledged.

Cost does not have to rise, and should fall. The reason completeness and cost are currently in tension is that one budget — page_cap — governs both fetching and extraction. Separate them: crawl exhaustively over cheap HTTP, extract selectively with deterministic parsers first and Gemini only for genuinely ambiguous prose. That gives you the full page inventory, an exact account of what has not been extracted yet, and the ability to extract the remainder later without re-crawling a single page.

The seven Critical items in section H are the ones that cause silent loss today. Four of them are small, local changes — the discovery union, the filterUrls anchor, surfacing truncation, and the DLX. Those four are worth doing regardless of whether the frontier rewrite is scheduled.
