One chat per visit, one contact per person

Ending a widget chat should close it, so a returning visitor starts fresh. The visitor page should summarise the person across all their chats, and show each chat with its own summary. Nothing below is built; it waits for your review.

What you decided

When a chat closes
When the visitor confirms the end. The open widget keeps showing it; their next visit opens a fresh chat.
Summary emails
One per chat that ends (today: one per visitor, ever). The wrap-up offer can appear again in a new chat.
Visitor page card
"Chat summary" becomes Contact summary: the whole person, from their profile and every chat.
Activity
Each chat appears under a short topic title and its date ("Scholarships for the MEng · Today"), with its own summary, among the other events. Before its summary exists it reads "Chat on 1 Oct".
01

The model

  • A chat is one ai_counselor_sessions row. It's open while ended_at is null; at most one open chat per visitor per widget.
  • A visitor (the tenant ai_widget_visitors row) stays one person across chats: profile, lead status, contact card, and the contact summary.
  • Each chat keeps its own summary on the session row, in the shape the card already renders: brief, still open, next step, course.

03

Visitor's side (widget routes)

  • findByVisitor returns only the open chat. So /guest/session gives an empty thread after an end, and the next message starts a new chat.
  • POST /guest/conversation-end with end: after today's work, set ended_at on the open chat. The learning signal that reads the chat runs first.
  • When a new chat starts for an existing visitor, reset the per-chat fields on their row: conversation state, the wrap-up offer counter, and the summary status, so the next end sends a new email. The contact card is not asked again.
  • The summary email's de-duplication key gains the chat id, so each chat gets exactly one.

05

Summaries (the existing summary worker)

  • Chat summary, per chat, refreshed after every message: each visitor message with its AI reply, each message while staff handle the chat, and each staff reply. It runs in the background once the reply has been sent, so the visitor never waits for it. It also returns a title of at most six words naming the topic ("Scholarships for the MEng"), which labels the chat in Activity and the Inbox dividers.
  • Two messages close together never overwrite each other with an older summary: a refresh only saves if the chat hasn't moved on while it was being written. If it has, the next message's refresh covers it.
  • Contact summary, per visitor. Built from the profile and every chat's summary, not the raw transcripts, so it's one short call. Rewritten at most daily, and only when a chat summary or the profile changed since.
  • The summary email covers only the chat that ended.

07

Left as is, and risks

  • The rating stays one per visitor (the latest). Activity shows it next to the chat it followed. Per-chat ratings need one more column; say if you want them.
  • Signing up adopts only the open chat into the new account; ended chats stay with the visitor record.
  • Model cost: one small extra call per message for the chat summary (it reads only that chat), plus at most one contact summary per visitor per day.
  • Rolling the migration back would delete all but the newest chat per visitor (the old index allows only one).
